## 第一部分 · 三个 Dockerfile 规格

> 落地约束（通用）：工程师只创建 `bank-core/Dockerfile`、`agent-service/Dockerfile`、`web-app/Dockerfile`、`web-app/nginx.conf` 与三个 `.dockerignore`；不得改动 `deploy/docker-compose.yml`（除非 §1.2.4 的 volume 决策经主理人批准）。

### 1.1 `bank-core/Dockerfile`

**冻结要点落实对照**（doc 05 §3.1 第一行）：

| 冻结要点 | 落实方式 |
|---|---|
| python:3.12-slim | `FROM python:3.12-slim` |
| 安装 requirements | `pip install --no-cache-dir -r requirements.txt`（fastapi/uvicorn[standard]/sqlalchemy/pydantic/httpx，版本以文件为准） |
| 复制 app/ | `COPY app/ ./app/`（只复制 `app/`，tests/scripts/data 不进镜像） |
| 启动时自动建表+幂等种子 | **应用层已实现**（F1）：`main.py` lifespan 内 `create_all` + `seed_if_empty`。Dockerfile 不加 seed 命令，避免双写竞争 |
| `uvicorn app.main:app --port 8100` | CMD 显式 `--host 0.0.0.0 --port 8100`（容器内必须绑 0.0.0.0，仅 `--port` 不够） |
| 无 `--reload` | CMD 不出现 `--reload` |

**规格（指令级）**：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
# 依赖层单独 COPY，利用构建缓存
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
# 业务代码（models/routers/scheduler/seed 全在 app/ 内）
COPY app/ ./app/
# 与 deploy/docker-compose.yml 的 environment 对齐（DB_PATH=/app/data/bank.db）
ENV DB_PATH=/app/data/bank.db
RUN mkdir -p /app/data && chown -R appuser:appuser /app        # 非 root 运行（见下）
USER appuser
EXPOSE 8100
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8100"]
```

补全说明（合理技术补全，均有据可依）：

1. **非 root 用户**：`python:3.12-slim` 无内置非 root 用户，需先创建。规格要求在建 `appuser` 后再 `chown /app/data`，否则 SQLite 建库 `PermissionError`。做法：
   ```dockerfile
   RUN useradd -m -u 10001 appuser && mkdir -p /app/data && chown -R appuser:appuser /app
   USER appuser
   ```
   - 命名卷 `bank-data:/app/data` 首次挂载会**继承镜像内 `/app/data` 的属主**（appuser），权限闭环，无需额外处理。
   - 若工程师求稳可退化为 root 运行（删 `USER` 两行），功能无差；非 root 是给安全自评报告 §6「沙箱隔离」加分的可选项，P1。
2. **`PYTHONDONTWRITEBYTECODE=1`**：容器内不落 `.pyc`，与 `.dockerignore` 双保险。
3. **`PYTHONUNBUFFERED=1`**：种子写入/调度器日志实时可见，`docker compose logs` 排障需要。
4. **不要 HEALTHCHECK 之外加复杂度**：compose 未定义 healthcheck，`depends_on` 为容器级启动序；bank-core 启动 <2s，不引入 `wait-for` 类脚本（冻结设计没有，别加）。

### 1.2 `agent-service/Dockerfile`

**冻结要点落实对照**（doc 05 §3.1 第二行，"同上 + 启动期校验 LLM_API_KEY 存在（缺失则进入 LLM 降级模式仍可演示查询）"）：

| 冻结要点 | 落实方式 |
|---|---|
| python:3.12-slim + requirements | 同 1.1 模式；依赖含 langgraph / langchain-core / langgraph-checkpoint-sqlite / aiosqlite / openai / websockets / pytest（以 requirements.txt 为准） |
| 复制 app/ | `COPY app/ ./app/`——**`app/static/demo.html`、`app/static/im.html`、`app/llm/prompts/*.md` 随目录进入镜像**，均为运行必需 |
| 启动期校验 LLM_API_KEY | **应用层已实现**：`config.py` 默认 `""` + `llm_enabled()` 降级（规则路）。Dockerfile 只做文档性默认 `ENV LLM_API_KEY=""`，**不得**在 Dockerfile/入口做 `RUN test -n $LLM_API_KEY` 类强校验——那会杀死"无 key 演示查询"这一冻结行为。可观测性要求：确认 `main.py` lifespan 在无 key 时打印一行降级警告（无则请工程师补，属应用层 P2） |
| `--port 8200` | CMD `--host 0.0.0.0 --port 8200` |

**规格（指令级）**：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/
# 与 compose 对齐；LLM_API_KEY 由 compose 注入（${LLM_API_KEY}），缺省为空 = 规则降级路
ENV BANK_CORE_URL=http://bank-core:8100 LLM_API_KEY="" LLM_PROVIDER=deepseek LLM_MODEL=deepseek-chat
RUN useradd -m -u 10001 appuser && mkdir -p /app/data && chown -R appuser:appuser /app
USER appuser
EXPOSE 8200
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8200"]
```

#### 1.2.4 data 目录（agent.db）持久化决策 —— 重点裁决项

**事实**（F3）：`AGENT_DB_PATH` 默认 `<repo>/agent-service/data/agent.db`（容器内 `/app/data/agent.db`），审计、熔断器、pending_actions、mfa_challenges、LangGraph checkpoints **共此一库**；compose 中 agent-service **没有 volume**，即库落在容器可写层。

| 方案 | 容器重建后 | 写入路径 | 评价 |
|---|---|---|---|
| A. tmpfs（`tmpfs: /app/data`） | 全丢（停止即丢） | 内存 | **不推荐**：SQLite WAL 在 tmpfs 上无收益反多一份内存拷贝；与"演示中途重启恢复"诉求正相反；且"重置"本就不需要它来保证 |
| B. 容器内目录（现状，零改动） | `docker compose restart` 保留；`down` + `up`（重建容器）丢失 | 容器可写层 | 可接受兜底：M4#3 验收场景是"干净机器 up 三分钟可演示"，本就不依赖旧数据。**但**：若演示中途重建容器，在途的红色转账待办卡 / MFA challenge / 审计证据全丢——演示事故 |
| C. 加命名卷 `agent-data:/app/data`（compose +2 行） | 跨重建保留 | Docker 卷 | **推荐**：审计回放与安全自评证据可跨重启取材；中断恢复（checkpoint）在容器重建后仍可用；重置仍是"一步"——`docker compose down -v` 或 `docker volume rm`，与 doc 05 §3.3 `reset_demo.ps1` 目标一致 |

**架构结论：选 C（加命名卷），B 为冻结设计不动时的兜底。** 取舍理由：

1. 答辩现场最怕的是"重建即失忆"——方案 C 让 `agent.db`（审计六类事件是安全自评报告的直接取材、checkpoint 是"刷新不丢待办卡"考据的底座）活过容器生命周期。
2. 成本极低：compose 增 2 行（`volumes:` 段加 `agent-data:`，service 下加 `- agent-data:/app/data`），属对冻结设计的**微小修订**，需主理人批准后由工程师执行（见 §5-R1）。
3. 若团队决议严格不动 compose：采用 B，Dockerfile 保持 `RUN mkdir -p /app/data`（应用层本就 `makedirs`，双保险），并在 README/演示手册注明"agent 侧数据随容器重建重置"。
4. 无论 B/C，**都不要 tmpfs**。

另注：非 root（`USER appuser`）+ 命名卷时，卷首次挂载继承镜像内 `/app/data` 属主（appuser），权限闭环；若工程师选 root 运行则无此虑。

### 1.3 `web-app/Dockerfile`

**冻结要点落实对照**（doc 05 §3.1 第三行："node:20-alpine → nginx:alpine；`npm ci && npm run build` → dist 复制到 nginx；nginx.conf 配置 /ws 与 /api 反代到 agent-service:8200"）：

#### 1.3.1 规格（指令级，多阶段构建）

```dockerfile
# ── 构建阶段 ──────────────────────────────
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build            # = vue-tsc --noEmit && vite build → dist/

# ── 运行阶段 ──────────────────────────────
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

补全说明：

1. **`COPY package.json package-lock.json ./` 先于全量 COPY**：依赖层命中构建缓存，改业务代码不重装依赖。
2. **为什么COPY 到 `/etc/nginx/conf.d/default.conf`**：官方 nginx 镜像的 `nginx.conf` 在 `http{}` 内 `include /etc/nginx/conf.d/*.conf`，写入该路径即**覆盖默认 server 块**；因此我们的 `nginx.conf` 只需包含一个完整 `server{}` 块，**不需要** `events{}`/`http{}` 外层（工程师最常犯的错在此，需在代码评审卡死）。
3. **基础镜像版本建议**：`nginx:alpine` 符合冻结表述；若求可重复，钉 `nginx:1.27-alpine`（P2 可选，不强制）。
4. **构建阶段无需 `python`/`git`**：`npm ci` + `vite build` 纯 Node 链，alpine 体积小、拉取快（M4#3 三分钟目标友好）。

#### 1.3.2 ⚠ `npm ci` 前置条件（F5，硬阻断级细节）

`web-app/` 当前**不存在 `package-lock.json`**，而 `npm ci` 无 lock 文件直接报错退出。处置（工程师按序执行）：

1. 本地（Node 20）进入 `web-app/` 执行 `npm install` 生成 `package-lock.json`（与 `package.json` 声明的 echarts/element-plus/pinia/vue/vue-echarts/vue-router + devDeps 一致）；
2. **将 `package-lock.json` 纳入 git 初始提交**（它是可重复构建的一部分，不是产物）；
3. Dockerfile 用 `npm ci`（锁版本、装得快）。
4. 若团队决议不提交 lock：Dockerfile 降级 `npm install`，须接受"不同时间构建出的依赖树可能不同"——**不推荐**，与 M4#3 可重复部署目标相悖。

## 第二部分 · `web-app/nginx.conf` 完整规格

**落点**：`web-app/nginx.conf`，由 `web-app/Dockerfile` 复制到 `/etc/nginx/conf.d/default.conf`（内容 = 单个 `server{}` 块，无 `http{}`/`events{}` 外层）。

**规格全文（工程师照此落地，允许格式微调，语义项不得缺项）**：

```nginx
server {
    listen 80;
    server_name _;

    # ── gzip 基本项（静态资源压缩；text/html 由 nginx 默认开启）──
    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1k;
    gzip_proxied any;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    # ── SPA history 模式 fallback（router.ts = createWebHistory）──
    # /login /chat /audit/:traceId /im 深链直达与刷新均落到 index.html，交 vue-router
    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # ── 静态资源缓存（可选 P1：带 hash 的构建产物可长缓存）──
    location ~* \.(?:js|css|svg|woff2?|png|jpg)$ {
        root /usr/share/nginx/html;
        expires 7d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # ── REST 反代：前端 api/http.ts 走相对路径 /api/... ──
    location /api/ {
        proxy_pass http://agent-service:8200;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # ── 健康检查透传（可选 P1）：前端 getHealth() 打 /health，
    #     不加则会被 SPA fallback 返回 index.html(200)，前端解析 JSON 失败判 down ──
    location = /health {
        proxy_pass http://agent-service:8200;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
    }

    # ── WebSocket 反代：ws/client.ts 连 ws://<host>/ws/web?session=... ──
    location /ws/ {
        proxy_pass http://agent-service:8200;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;        # WebSocket 握手必需
        proxy_set_header Connection "upgrade";         # 同上
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;                           # WS 流式帧必须关缓冲
        proxy_read_timeout 3600s;                      # 长连接：60s 会被 nginx 掐断
        proxy_send_timeout 3600s;
    }
}
```

**关键规格说明（验收对照用）**：

1. **`/api` 与 `/ws` 反代目标**：`http://agent-service:8200`——与 compose 服务名/端口一致（冻结要点原文）。
2. **WebSocket 三件套**：`Upgrade`/`Connection "upgrade"` 头 + `proxy_http_version 1.1` + `proxy_buffering off`，缺一不可；`proxy_read_timeout 3600s` 防演示静默期（如等用户点确认卡的 5 分钟）被 nginx 断连——这是 WS 反代与普通反代**唯一必须拉开差异**的项。
3. **SPA fallback**：`try_files $uri $uri/ /index.html`——`/audit/:traceId`（回放深链，评委可能直接粘贴 URL）与 `/im` 都依赖它；`createWebHistory` 无此配置则刷新即 404。
4. **`location = /health`**（P1 可选）：不配也能跑（前端 catch 后显示 down 徽标），配上前端状态灯语义正确。
5. **DNS 解析时序（主用方案）**：`proxy_pass http://agent-service:8200` 字面主机名在 nginx **启动时**解析。compose 默认网络下，`depends_on: agent-service` 保证容器先创建（创建即注册 DNS），web-app 启动时解析必成功，无鸡生蛋问题。已知残余风险：agent-service 容器**重建**后 IP 变化，nginx 不 reload 会连旧 IP——演示场景几乎不触发；加固方案（P2 可选）：`resolver 127.0.0.11 valid=10s; set $upstream http://agent-service:8200; proxy_pass $upstream;`（运行时解析，启动不依赖对端在线）。**二选一，不要混用**。
6. **gzip**：`gzip_types` 不含 `text/html`（nginx 对 text/html 默认始终压缩，显式写出反而冗余）；不含已压缩格式（woff/图片无益）。
7. **路由直达验证清单**（部署后 QA 逐条点）：`/` → 跳 `/chat`；`/login`；`/chat`；`/im`；`/audit/tr_demo`（任意 trace，无数据显示空态而非 404 页）；任意不存在路径（如 `/xyz`）→ fallback 后 router 通配 redirect 回 `/chat`。

### 4.2 提交结构建议：**一次性初始提交**

**推荐**：仓库根执行一次 `git init` + 一次 `git add -A` + **一条**初始提交：

```
chore: 初始化智银 Agent 仓库（三服务源码 + 文档 + 部署编排 + 脚本）
```

理由：

1. **初始导入无演进史价值**：评审与评委看最终工作树；按服务拆成 4 个 commit 只是制造"虚假历史"（同一天、同一作者、彼此不可独立构建）。
2. **交付完整性优先**：任何单模块的中间 commit 都不可独立运行演示（前端缺后端、后端缺部署文件），中间态 commit 没有存在的意义；一次性提交保证"任意一次 clone 都是完整可运行系统"。
3. **M4#3 硬阻断的时间线**：Dockerfile/nginx.conf 若在初始提交时已就绪 → 一并入库；若未就绪 → **就绪后立即补第二个提交** `feat(deploy): 补齐三服务 Dockerfile 与 web-app nginx 反代配置（M4#3）`，绝不把未提交的部署文件带进答辩现场（换机/误删即事故）。
4. **防漏文件**：一次 `add -A` 比分组多次 add 更不容易漏（漏一个 Dockerfile = 部署链条断裂）；提交前按 §4.1 末尾清单核对"必须入库"项即可兜底。

**备选（不推荐，仅当团队想用历史辅助 review）**：`chore: 初始化` → `feat(bank-core)` → `feat(agent-service)` → `feat(web-app)` → `docs: 文档与脚本` 五连。若采用，务必保证最后一个 commit 完成时树是完整可演示态。
